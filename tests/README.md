## 测试政策

[AGENTS.md](../AGENTS.md) 原文：

> **测试政策（用户 2026-09-25 强制要求："不要写太多的测试了！除非非常有必要，不写就会很有问题的时候才写"）**：测试只在两种情形写——①钉的是原版量得的事实（static-derived／模拟器实测），且没有现成套件覆盖；②不写就会让门禁抓不到会伤玩家的回归。其余一律不写。重制自己随机流的产物（开场等级数组、某个种子下的流状态、动作计数）**不钉数值**，只断言不变量；不为"消融能变红"而加测试；不为机械小改加复述实现的测试；一条 lane 默认不新增测试文件，优先在现有套件里加一两个代表性用例。任务书验收只写玩家可见结果与原版对照结果行。

本目录的落实：

- **局面只经真实入口造**：新用例从 `static func` 夹具出发，走玩家／AI 同样走的公开入口（`choose_command`／`move_unit_to`／`attack_target`／`attack_coord`／`use_item`／`step_ai_turn`……）到达要测的局面；不用 `Loop._set_unit_defeated`、`Loop._return_to_player` 这类私有函数拼场景——拼出来的局面玩家到不了，测试绿不证明真实路线对。现存用法是旧账，不照抄，改到时换成真实路线。
- **随机流只经 TestSuite**：读写与比较用 [TestSuite](support/TestSuite.gd) 的 `stream_of`／`set_stream`／`seed_stream`／`no_draw`／`continues`／`carries_no_stream`，桩用 `zero`／`high`／`no_rng`；套件里不直接写 `damage_random`／`global_random` 的内部键，流的存储形状变了只改 TestSuite 一处。
- **规模按手写断言点和耗时报，不按 `checks=`**：写在循环里的一处 `check(` 会被计成上千次，`checks=` 只用来核对合并前后没有丢断言。2026-09-26：`tests/` 下 203 个 `.gd` 共 59622 行，手写断言点 8884 处（`grep -ohE '(^|[^[:alnum:]_.])(check|_assert_true|_assert_eq)\(' tests/*.gd tests/*/*.gd | wc -l`），规则套件 49 个，`run_all` 耗时见 [Harness](#harness)「跑全部规则套件」行；`tools/test_*.py` 139 个文件共 16022 行，`self.assert*` 3751 处。
- 一次性诊断脚本放 [diagnostics/](diagnostics/)，用完即删。

### 快钟（FAST_CLOCK）

`verify_runner.py godot` 只给 `FAST_CLOCK_SUITES` 里的场景套件加 `--fixed-fps $HSL_TEST_FIXED_FPS`（默认 60）：每个 process step 恒 1/60 s、不睡帧，SceneTreeTimer 与 tween 都跟这个引擎钟；`HSL_TEST_FIXED_FPS=0` 让全部套件回实时钟。快钟不是加速——它把「墙钟」和「引擎时间」拆开了，所以一个套件能不能上快钟只看它的等待分别在等哪个钟：

| 等待 | 实时钟下的写法 | 快钟下 | 改法 |
| --- | --- | --- | --- |
| 场景逻辑推进（走路、菜单滚动、淡入、状态到期） | `await create_timer(秒)` | 按 1/60 步照常成立 | 不改 |
| 开机后固定帧数再断言时间线已推进（首帧 delta 在实时钟下是整段加载时间≈3 s，快钟下 1/60 s） | `await process_frame` ×2 后断言 `music.playing` | 时间线才走了 33 ms，断言失败 | `TestSuite.await_condition(tree, func(): return 条件, 帧上限)` 等条件本身；上限按帧数不按秒；超限记一条「timed out waiting for …」再照常跑原断言 |
| 音频线程释放流（`AudioStreamPlayer.finished`、结尾 resources still in use） | `await create_timer(0.2)` | 只等到几 ms 墙钟，报泄漏（实时钟下紧跟长同步帧同样如此） | `TestSuite.settle_wall_clock(tree, 秒)` 按墙钟 spin 帧；`quit` 前的最后一次等待用 `TestSuite.settle_audio_before_quit`（另核对播放对象已释放） |
| 墙钟 deadline 轮询（`Time.get_ticks_msec() < deadline` 里 `await create_timer(0.01)`） | 原样 | 只是轮询更密 | 不改 |

断言内容（等的是什么、期望值）在两种写法下都不变；上快钟的套件必须在实时钟下也通过。现在在快钟上的场景套件：battle_sweep、story_mode_walkthrough、story_scene、battle_scene_runtime、title_screen、system_menu、campaign、opening_token、walk_camera_follow，深门的 story_mode_explorer、autoplay_sweep。未上快钟的 30 个场景套件（P2b 普查，负载 30–60 下实时钟／快钟秒数）：手动驱动 `_process` 的 CPU 型套件快钟不省甚至更慢（action_handoff 46／69、script_wait 15／25、priest 4／10、stat_magic 16／19，这两个 09-26 已并入规则套件 support_magic）；普查里看似省 10 s 的 presentation_contract／status_effect／ai_navigation 在空载复测为 3／3、6／6、14／12 s，差异是负载噪声；其余每个只省 0–5 s（combat_aftermath 37／32、ai_support 24／20、large_actor 17／15、battle_reward 20／17、magic_experience 13／9，其他 ≤ 3 s）——不值一次改动与一份 FAST_CLOCK 例外，保留实时钟。

[tools/godot.sh](../tools/godot.sh) 固定当前项目路径并共享严格诊断：进程非零、SCRIPT ERROR／ERROR 或资源泄漏均失败，不能只看末尾 PASS。它只执行给出的 Godot 命令，不自行跑全量或清缓存；快门保留导入缓存，`--full` 才删。
