# Battle systems contracts

## Attack and defense enhancements

Permanent gains are a different source layer: `PermanentCapabilityRules` validates nine acquired offsets, never overwrites `growth_profile.source`, and passes a copied effective source into the common job refresh. ItemResolution v2 commits actual inventory, one sampled increment, the derived profile and receipt together. Intrinsic resistance is capped80 before job/equipment computation; displayed resistance is capped80 afterwards. Display saturation alone does not make an item useless. Buff expiry/Dispel never remove acquired values, and current-round slots remain a snapshot until the ordinary next-round rebuild. Checkpoint validates offsets, derived values and the historical item proposal without replaying it. [Native boundaries and implemented routes](../evidence_packets/static_reverse/original_permanent_items.md).

Both campaign carry policies include `permanent_gains`. Matching actor IDs/source codes replace that field on the fresh template before shared refresh; no old temporary status, item sequence or derived cache is captured. JSON numbers are canonicalized to integers only after source/domain validation, so a fractional or over-cap saved value cannot be truncated into validity. Current-battle retry reuses entry gains, separate-party transitions leave unmatched actors unchanged, and a new campaign starts with empty gains. The isolated [two-process review](../evidence_packets/runtime_observations/permanent_items/README.md#跨战斗与跨进程补充) supplements the original single-battle routes.

`StatEnhancementRules` owns no battle dictionary. It validates optional packed attack_up/defense_up/resist_up words and proposes flat-power merges, expiry and selective dispel (退魔 clears only the attack／defense words; `resist_up`, the 魔障壁 AllUp word, adds `rand(14)+7` per cast up to 20 and raises all five live resistances in the shared refresh, cap 80, [skill function bits](../evidence_packets/static_reverse/original_skill_function_bits.md)). `StatMagicRules` uses original numeric calls and current equipment; `SkillResolutionRules` prepares the entire target set before RNG, pays once, and converts each contribution through the existing EXP helper. Self-target changes exclude HP/MP so they cannot overwrite the caster payment.

`ProgressionRules` derives physical attack/defense from source growth plus current equipment plus each active high-word value once, and adds an active `resist_up` strength to the five resistances before the 80 cap. Equip/level/restore use the same path; stale enhanced derived values fail validation. `TurnEndRules` v4 proposes all final-action events; PlayLoop validates any expiry refresh before committing resources/RNG/queue. First extra actions never execute that tail, paralysis executes one, terminal outcomes none. Death clears the words and derived values along existing footprint cleanup.

`AISupportPlanning` adds missing matching buffs to source bucket5 and the independent ai_help_attack priority. The native scan excludes self and existing matching positive states. Dispel is offensive and requires a current removable enhancement; a new independent AI action builds new candidates after the first removal. Cost, silence, paralysis, movement capability and no-effect rejection remain shared with the player. [Original evidence and exact boundaries](../evidence_packets/static_reverse/original_stat_magic.md).

本页只解释当前战斗系统的提交边界。先读 [架构入口](../ARCHITECTURE.md)，按改动选下面的章节；产品状态与下一项任务只看 [PROJECT](../PROJECT.md#next-steps)。路径以仓库根为基准，纯规则位于 game/sim，唯一状态入口位于 game/sim/loop/BattlePlayLoop.gd（合同门面；同目录 `BattleLoop*.gd` 是对同一 loop 字典操作的静态模块，见下方模块表）。

## Scenario, queue and combat

### `BattleScenario.gd`

`BattleScenario` 负责可复用的 JSON 加载、schema 校验、resource path、unit coordinates、viewport、projection 与 command flag 规范化；不包含任何第一战剧情规则。

**Unit 合同**：`playable_units`／`script_actor_templates[*].actor`／`content/generated/hsl/actors/*.json` 的 actor 与 carry 合并后的名册共用一份 JSON Schema [`content/schema/unit.schema.json`](../../content/schema/unit.schema.json)（`hsl_unit.v1`，draft 2020-12 子集），由 `tools/hsltools/schema/unit.py` 从全部 tracked 单位**推导现状**，顶层键逐个显式分类：`RULE_KEYS`（规则模块真正读的 27 键，逐键写消费者；其中全部 tracked 单位都带的 20 键为 `required`；`player_mode`／`object_hit_point` 是组装器按对象安装字写的可选规则键，见[阵营位读法](../evidence_packets/static_reverse/original_player_mode_sides.md)）、`PROVENANCE_KEYS`（14 个证据台账 `<ledger>_evidence_tier`／`<ledger>_source`／`position_note`／`attack_range_evidence`／`install_source`，只透传、永不必需——续集作者一键不写；缺省的 `<ledger>_evidence_tier` 由 `UnitSchema.evidence_tier` 读作 `authored`，枚举含该值）、`RUNTIME_PROPERTIES`（运行时增补键，一律可选）；未分类的键让 `hsl generate unit_schema` 失败。`combat_profile`／`growth_profile`／`status_counters`／`equipment[]` 分层 `additionalProperties=false`，`battle_actor_role`／装备槽／`*_evidence_tier` 为枚举。两侧校验同一文件、同一子集、同一首个违规文本：Python `hsltools/schema/validate.py`（`LevelBattleTask.render` 渲染后）与 `game/sim/UnitSchema.gd`（`BattlePlayLoop.create` 对 scenario 名册在 `BattleScenario.units` 归一化后、`ActorInitialization` 之前；脚本演员模板归一化后；`apply_campaign_carry` 在 `CampaignCarryRules.apply` 之后）。产品路径违规明确失败 `scenario_error = "unit_schema:units[<id>].<path>: <reason>"`；调用方自带 `units` 的 `create` 视为内存态不校验。`tools/test_hsl_unit_schema.py` 含第九波两类形状（装备写成 int 列表、键放错层级）的负向回归。`BattleSceneRuntime.scenario_path` 默认为 `DEFAULT_SCENARIO_PATH`＝`content/battles/battle_051.json`（战役 `start_level` 指向同一文件）；其他 scenario 经 campaign hand-off 或直接赋值注入同一 runtime seam。

### `BattlePlayLoop.gd`

当前 battle state 与操作：select、command、movement、revert、attack、wait、stepped AI、outcome。它不负责 UI 或资源解析。

**模块表（S8 拆分）**：PlayLoop 是合同门面＋玩家指令流（选择／菜单、移动、攻击选目标、`_settle_action` 行动预算、`_advance_current_actor` 唯一队列推进缝、`_finish_ai_or_continue` 回合钩子）＋全部模块共用的单位查询／写入（`_unit`／`_set_unit_*`／`_are_enemies`／`_queue_actors`……）。其余职责是同一 `game/sim/loop/` 下、**对同一 loop 字典操作的静态模块**：不持状态、不复制合同、经 `const Loop = preload(PlayLoop)` 回引用共用缝（Godot 4.7 允许静态模块间的 preload 环）。公开合同函数与 Runtime／Checkpoint 触达的内部缝（`_reward_input_error`、`_resolve_outcome`）在 PlayLoop 文件尾**转发**，调用方仍只见 `BattlePlayLoop.*`；只有测试触达的模块内部缝不转发，测试直接 preload 模块（`LoopAI`／`LoopCombat`／`LoopInventory`／`LoopRewards`／`LoopScript`）；测试经 `Loop.X` 访问的规则模块常量（`Loop.BattleScenario` 等）以别名从拥有它的模块再导出。

### `BattleOutcome.gd`

The decided battle result is one structure under `battle_outcome` (LoopKeys.BATTLE_OUTCOME):
`{"result": "victory"|"defeat", "reason": …}`, `{}` while the battle is undecided. Victory
reasons name the deciding win status' head condition — `escape`
(actCheckPlayerArrivePos／actCheckAnyPlayerArrivePos), `enemies_cleared`
(actCheckEnemyTotalNumber), `boss` (actCheckPlayer／actCheckEnemy／actCheckPlayerHPLow／
actCheckEnemyNumber), `script` (anything else) — via `WinfailScenarioRules.outcome_for`;
`DevelopmentBattleRules.victory` reuses `escape` and `enemies_cleared`. Every fail status and the
remake party wipe share `{"result": "defeat", "reason": "fallen"}` (`WinfailScenarioRules.DEFEAT_OUTCOME`;
`winfail_runtime.resolved.key` still tells `party_wiped` from a script fail key). Readers ask
`BattleOutcome.decided／won／lost／reason` — no key parsing; `describe` (`victory/escape`) is the
report-line spelling only. `BattleScenarioRuleAdapter.victory_state` returns the structure (`{}` for
ongoing); `winfail_runtime.resolved.outcome` stores the same structure; the deciding status' own
actMessage lines are keyed `WinfailScenarioRules.TERMINAL_DIALOGUE_KEY` (`"terminal"`) in
`winfail_runtime.dialogue` and the presentation's shown-story cursor. `BattleCheckpoint` v4 writes
the structure and refuses v3 (key-string outcomes) by name — no migration.

### `TacticalGridRules.gd`

纯移动可达、cost/path envelope 和 attack range。正常武器格子由 `attack_pattern_cells` 投影；PlayLoop 的 weapon_code 经 generated attack_ranges 中 ITEM 对照表选择 RANGE offsets，不再在单位上重复保存范围名。输入为 units/tiles/map size，无 scene state。

`RangePropagationRules`（纯函数）按原 `0x40f8b0`／`0x4100e0` 把 RANGE 记录在地图字（WRD `0x4000` 与占位者侧位，不读高度）上传播：`BattlePlayLoop.weapon_cells` 给玩家（mode 2）和其他单位（`0x40bab0` mode）算武器格，`attack_cells`、反击与高亮都读它；`skill_terrain` 让施放范围走 mode −1。`attack_pattern_cells` 仍是 AI 规划和没有矩阵数据时的平铺投影；技能悬停预览与效果区域结算也仍平铺。规则表与调用方见[原武器射程](../evidence_packets/static_reverse/original_weapon_ranges.md#地形传播)。

当前移动预算只读unit.move_point；源基础base_move_point用于初始化／装备／成长刷新，不能再当路径预算。`MobilityRules`从基础加每个当前装备槽的add_move，最后夹0..12；玩家可达格／路径、全图AI搜索和行动前缀继续使用同一当前值，不绕过障碍／占格成本。详见[装备移动力](../evidence_packets/static_reverse/original_equipment_mobility.md)。

`ActorTraversalRules`从源traversal初始化飞行／不阻挡／体型，支持size_type0／1；单格角色使用地面阵营mode2/3/7或飞行mode6。当前装备／成长不改固有能力，恢复校验与源声明一致。地面允许同侧经过、尊重敌人mask和高差，飞行忽略高差但保留硬障碍；最终停留另检查普通占格与no-stop。`TacticalGridRules`以临时来路方向保持邻接成本，返回`reachable_by_coord`（可停）和`transit_by_coord`（可经过不能停），每条path带同一累计cost及path_stops。全图AI只从合法格选目标位置，行动前缀退到预算内最后合法格；状态／占用变化后查询重新读取当前数据。单格来源见[通行合同](../evidence_packets/static_reverse/original_actor_traversal.md)。

`FootprintRules`从唯一actor锚点派生单格或3×3；地面大角色逐候选检查整块占用与高度255，不能套用同伴／no_block的单格挤过例外；飞行整块可经过普通占用而不能停在其上。大小角色都用四邻扩展，原边缘查询保留裁剪语义。移动／撤销／死亡后由现状态重新派生占用，不保存第二张可变占格表。普通武器大体型索引为min(20,源武器索引+范围装备位+17)，技能施放范围仍从施法者锚点计算。目标的身体边缘可以进入攻击、反击、技能和道具邻接查询；区域效果按actor身份提交一次，保留实际点击格／空格中心。初始化、增援候选和Checkpoint验证源身体与整体落点，旧路径或目标失效时AI重新准备；详见[大型角色证据](../evidence_packets/static_reverse/original_large_actor.md)。

`WrdTerrainTiles`只接受保留原高字节h的v2包，不将旧b布尔值当高度；读取失败使PlayLoop初始化返回scenario_error。051／052源WRD的header、tile id及h可由离线工具重建SHA，源地形与运行时对象flags仍分开。均不新增另一份战斗状态。

### `CoreTurnQueue.gd`

证据门禁的 speed queue 与 BCMD 编号。它不是引擎 object process dispatcher。当前轮使用 rebuild 时保存的 `live_speed` 快照；`0x407510 → 0x4074a0` 推进到队尾 wrap 后才按实时 actor 速度重新执行 `0x407340`。因此成长刷新出的新速度不会追溯重排正在进行的轮次，而会在下一次 queue rebuild 生效；纯规则回归覆盖这一边界。

`CoreTurnQueue.cancel_pending`按原`0x407550`只禁用当前索引之后首个符合目标且启用的槽。它不改变当下反击、当前角色已获得的第二行动、单位存活或占格；被取消者本轮不进入新行动入口，也不执行麻痺／毒伤／回复尾部。`slots[].enabled`随存档保留，正常下一轮rebuild才恢复。队列输入先校验，Checkpoint另拒绝重复身份；详见[武器尾部与队列取消](../evidence_packets/static_reverse/original_weapon_effects.md)。

### `CoreCombatRules.gd`

combat profile、hit chance、damage、weapon apply、counter gate。PlayLoop `_resolve_exchange` 预判一次反击资格，先完成主攻击系列，再对存活防守者完成反击系列；`CombatSequenceRules`读取当前装备／源天赋决定各系列1或2击。每击独立命中／暴击／贡献，死亡截断剩余击与反击。结果仍由同一PlayLoop持有，presentation只读收据。未确认分支保留在evidence/unresolved字段中。

根收据是第一击，`followups`为其后各击，`counter`为反击系列；根不能冒充最后一击HP。播放、死亡和掉落用`CombatSequenceRules.strikes/outcomes`统一遍历。系列内部不升级；整个交锋完成后每参与者汇总贡献、装备倍率、一次入账与成长，避免先攻升级改变反击。击杀链在系列末更新，第一反击未杀不能抢先清除连续数。源極光之劍可换装，额外次数不叠加、不复制法术或Wait；详见[追加攻击](../evidence_packets/static_reverse/original_extra_attack.md)。

普通数值使用原0x409be0完整返回及0x409af0武器附加；原0x409bca是前函数后的填充。顺序为反击资格／概率→主攻击抽样→命中→命中后的暴击→实际HP／贡献→必要反击→最终发奖。反击80%在暴击前乘算。`queued_damage`保存前暴击量，`damage`保存impact量，`actual_damage`保存HP封顶量；后两者不能替代气力输入。必需概率、元素、区间与抗性在玩家／AI进入RNG前校验；`native_draw`保留rand0和原raw低伤害修正调用。见[普通／绝技原证据](../evidence_packets/static_reverse/original_ordinary_special.md)。

`WeaponEffectRules`在主攻／反击各自系列末端执行：每击实际HP→本击EXP换算，只有换算值大于0且无剩余追加击（或提前击杀）才进行取消10%→防护检查→附毒25%及持续／强度抽样，随后才结算系列气力。末击落空不回补前击机会，附毒不增加法术贡献；整场交锋完成才发最终EXP和升级。原HP0样例仍消费已证实的抽样，之后统一死亡清理。`weapon_effects`及`defender_after`只附在实际执行尾部的击收据中，不能挂到第一击或下一动作上。法术／支援／物品不调用该尾部。

A settled exchange (player `attack_target` and the AI's new combat receipt) scans
nothing: it records `action_attacker_id` next to `last_attack` — the remake's attacker
global `0x4c1ce8` and attacked list — and the action's completion scan (below) reads
them in the `attack` context, the only context in which
`actCheckPlayerAttacked`／`actCheckSerialPlayerAttacked` hold (and in which
`actCheckNotPlayerAttacker` can fail). Static basis:
[attack context](../evidence_packets/static_reverse/original_round_display.md#attack-context-static-derived-lane-r37-2026-09-28).

## Action completion

`ActionBudgetRules.outcome` returns transient changes and a result kind: keep actor, select movement/target, restore movement, await presentation or end action. It owns no battle dictionary. All player commands validate current living player, phase, completion and open Give session before mutation; operation-specific range/item/cost checks still apply. `_settle_action` applies flags to the sole PlayLoop, while `_advance_current_actor` is the one normal player/AI queue-advance seam. For a living actor it runs the status tail (poison／durations／kill chain, the original `0x40b910`), then scans win／fail／event statuses (`run_event_hooks` ＋ `_resolve_outcome`, the original `0x407510` → `0x408370` → `0x44ee20`), and only then calls `CoreTurnQueue.end_turn`; the wrap in `_finish_ai_or_continue` merely bumps `turn`. The scan runs in the `attack` context when the finishing actor attacked in this action (`_takes_attack_scan` consumes `action_attacker_id`; an extra action's first half clears it on repeat), and an actor that died in its own attack is scanned once without the tail (the original's death sequence `0x407510`). A round-N event therefore fires after round N's first completed action (Wait, item use, paralysis skip and offense alike), a decided outcome freezes before the queue advances, and a skipped dead slot scans nothing (the original removes it through `0x407720` → `0x4074a0`). Static basis: [round counter and cadence](../evidence_packets/static_reverse/original_round_display.md#round-counter-0x4c1bbc-and-actcheckroundnumber-static-derived-lane-e1-2026-09-27); `tests/run_event_cadence_tests.gd`. Attack/miss/special finish regardless of prior movement; scene waits for the complete cue/cutin/reward presentation before `finish_exhausted_action`. Repeated presentation does not advance the successor. Move cancellation restores only position and movement eligibility, then immediately enters `move_select`; committed inventory/equipment changes are retained. Runtime syncs from the accepted result and cannot move a mirror after a rule rejection.

`ExtraActionRules` adds the original action_twice gate before that seam's final status/queue tail. On the first completed action it reads current equipment and, when enabled, stores one pending repeat owned by the current actor, clears this segment's movement/offense flags and reenters the same player's menu or AI decision. The second completion clears the latch and advances normally regardless of intervening equipment changes. The queue is not duplicated, status/poison and kill-chain cleanup do not run between actions, and each independent strike/skill still has its own settled receipt and EXP. `extra_action` lives in the sole loop with owner_id/pending/sequence; death, departure and outcome clear it. Save/load checks ownership and preserves an already granted second action after removal; re-equipping cannot create a third. See [native gate and playable chain](../evidence_packets/static_reverse/original_extra_action.md).

取消选目标保留已接受的pending移动；取消移动才恢复整块占地及移动／施法阶段，既有装备、异常、资源和队列资格均保留。第二行动中的取消也不重发第一行动的武器效果、气力或EXP。动作接受后不能借取消退回未付费状态；完整演出结束前仍等待`offense_presented`。这是与“取消敌方未来槽”分开的现行交互合同。

`WinfailScenarioRules.reinforcement_deficits` 消费 winfail 的 `actCheckEnemyNumber` 事件（第一战 WINFAIL051 event 0／1：021 少于 3、026 少于 2 时在城门 (267,209) 插入一名），PlayLoop 在行动交接时经 `ScriptActorCreationRules` 从脚本模板补员，检查出生格占用和 WRD 阻挡；同一事件链里 `actChangePrevInsertObjectID N` 把刚插入的对象绑定为 token `N`（WINFAIL051 的信使 10000），随后同链的 walk-and-delete 由事务补全该对象的离场请求。Scene 同步时只创建缺失的 ActorRuntime；新单位由后续普通队列重建纳入，不另建增援队列。

## Inventory and equipment

`consumables.json` v2 derives starting inventory and item properties from PLAYERS/ITEM/RESOURCE. PlayLoop owns eight integer item-code slots per unit; 0 is empty, duplicates occupy distinct slots. JSON numbers are canonicalized to integers before lookup. `InventoryRules` inserts into the first empty slot and removes with left compaction. `use_item` heals or cures poison on self/living cardinal-adjacent ally, then ends the owner action including pending movement. No-effect uses, missing items, invalid phase and already-attacked use are inert; full-health poisoned targets can use antidote. Ordinary Use, Give, free Drop/Equip and movement/offense share `ActionBudgetRules`, consumed by PlayLoop `_settle_action`. Supported afflictions use the shared skill transaction; full native target eligibility and other status effects remain separate.

Give is `begin_give → confirm_give* → finish_give`. The sole PlayLoop stores `give_session={owner_id,action_used}`, `item_revision`, and both inventories. `InventoryRules.exchange` validates source/destination indices and expected codes, removes/compacts the selected receiver item if any, first-hole inserts the incoming item, and returns any displaced item to the sender. Full recipients permit explicit exchanges; automatic empty-slot insertion fails when full. No UI-held inventory exists. Returned code different from outgoing code ORs the session's action-used flag; same-code exchanges may reorder slots without newly charging an action. Only session exit consumes that action. Other battle commands cannot bypass the open session.

`BattleGiveView` displays immutable snapshots; `BattleItemPanel` holds only target/slot/code intents and previews. Confirmation checks the actual Button/view identity, captured request and monotonically increasing PlayLoop revision. Cancelled or already-accepted signals cannot authorize a newer identical proposal. Cancellation before confirmation restores gameplay state and exact slot order; revisions intentionally do not roll back. Previously confirmed transfers remain committed. A changed session exit commits pending movement; an unused exit preserves movement rollback. These confirmation and rollback choices are distinct from native held-item cancellation. Source paths and limits are in `original_give_exchange.md`.

Discard additionally uses `InventoryRules.discard`, checking the original ITEM `important` flag before removing a slot or committing an action. Missing discard metadata rejects explicitly. The panel shares that eligibility, disables protected rows and still rejects stale selection in its confirmation view; PlayLoop enforces the same rule independently. This is not the equipment `take_off` flag and does not introduce a transfer ban. Original command Data8 and target-cancel return paths are documented in `original_item_actions.md`; full action-consumption parity is still separate from the inventory transaction.

`EquipmentRules.replace` validates job/type/old-item take_off, then computes a proposed inventory/equipment exchange without mutating input. `BattlePlayLoop.change_equipment` additionally validates current living player, phase, supported job refresh, resource effects and weapon range, then commits inventory, equipped codes and refreshed attributes together. A removed weapon now uses the native empty-slot range0: no hostile ordinary target or counter, and no invented close-range fallback. 成长输入来自场景growth_profile和当前装备，面板只有未提交草稿。`ExperienceRules`独立恢复贡献、等级差、原随机折减及击杀连续数；PlayLoop将全目标量汇总、应用装备exp_x2后一次入账，Growth只接收最终量。零贡献／无剩余容量不发，死亡者不作死后成长。升级窗照原版必须当场分完才能关（右键／Esc 不关，原升級窗包 §2）；一次跨多级时未用点数预占剩余容量、一个窗给全部点数，是重制组合（原版每级一个窗，总数相同）。`LearningRules`在玩家新等级提交时取得魔法、确认基础属性分配时取得第一条可学绝技；初始声明、learned_skills、装备权限互不改写。新能力直接进入共享所有权／AI候选，尚未实现效果的能力仅记录并明确提示不可用。Aftermath在交锋／EXP之后显示已提交学习，GrowthPanel不预发技能。F9、换装、第二行动不重学或重复经验，来源见[成长生命周期](../evidence_packets/static_reverse/original_growth_lifecycle.md)。

成长及换装还从原source和当前装备重新计算普通反击／暴击：基础0分别置12／8，非零源值保留（Leonard为14暴击），然后加入装备增量。`EquipmentRules.effect_delta`提供当前武器的元素／low／high，替换后清除旧武器附加；source保留原值，不能把working概率重复叠加。Checkpoint同时校验必需物理字段和新配置摘要。

## Final-action resource recovery

`ResourceRecoveryRules` ORs the current equipment's mp_use_half/hp_auto_restore/mp_auto_restore flags; duplicate sources never quarter MP cost or repeat healing. `SkillResourceRules` still owns each spell's cost. `TurnEndRules.prepare` combines the existing poison/duration proposal with source HP-then-MP automatic restoration, using actual post-poison missing resources and current refreshed caps. Only the final action reaches this proposal; White Wings' first completion returns earlier. PlayLoop alone commits resources, a monotonically numbered last_action_end receipt, the shared saved damage stream `damage_rng` (DamageRandomStream, the same state exchanges, casts and items draw from) and the ordinary queue advance. Free equips/cancels and terminal outcomes do not recover resources, draw from the stream or revive actors.

Receipt before/after/effects/draws/rng are deterministic validation inputs, not another mutable actor. Checkpoint reproduces the proposal for consistency without applying it again; stat_refresh_policy/turn_end_policy participate in configuration compatibility. That saved stream is the original damage stream (0x42c780), not the unsaved global stream (0x458c10) that kill drops and birth carry draw. A later AI action freshly checks restored MP/HP, costs and legal positioning. See [native prefixes, inactive returns and limits](../evidence_packets/static_reverse/original_resource_recovery.md).

`hp_transfer_mp` follows both automatic restores, samples twice even at1HP and spends capped actual HP even when MP is full. `TurnEndRules` policy v2 records poison→auto_hp→auto_mp→transfer_hp→transfer_mp; only nonzero events display. Current equipment is ORed once, and only the last independent action executes the tail. `StatusApplicationRules.modifiers` likewise combines current equipment and source intrinsic protection; additive magic hit affects the damage hit gate only, while proc&4 reads its independent status probability. Protection does not cure an existing condition. Equip/growth/Checkpoint revalidate the same sources; see [casting equipment](../evidence_packets/static_reverse/original_casting_equipment.md).

## Rewards and checkpoints

`TreasureRules` is an optional source-backed proposal, consumed by the sole PlayLoop at a completed controllable actor action. The three formal Ohm/Gol chest contents come from original EVEF instance words, not drop RNG or default inventory. Moving/hovering/cancelling never grants them. The committed ledger records exact source contents and temporarily holds the current queue/extra-action/status-tail lease; the existing pickup UI closes before that same action resumes. Repeated identical items retain separate source slots. `BattleTreasurePresentation` reads the receipt and existing box nodes for its remake fade/sound, blocks later controls while busy and never awards an item. Each chest carries `hidden` (its OBS template has no `objattrATTACKFLAG`, [original](../evidence_packets/static_reverse/original_treasure.md#隐藏宝物)); `TreasureRules` requires it but collects both kinds identically. The presentation's one read point is `reveal_all_chests` (default false = original) through `chest_drawn(chest)`: an undrawn chest has no sprite and no hover hint, and its discovery plays `get_treasure` (sfxGetTreasure) instead of the accept sound.

Reward `sequence` is monotonic across combat and discovery, while `combat_sequence` identifies only the last settled fight. Checkpoint binds the current source kind, chest receipts and visual cursor without replaying them; invalid queue indices and noninteger cursors reject before access/coercion. `CampaignCarryRules.pending_rewards` namespaces unclaimed items across ordinary-party handoffs. Valid carried inventories normalize to integer codes, and the loot preview asks the same pure inventory insertion rule rather than misreading JSON 0.0 as a full slot. The development AI fast-forward yields at pending loot, just as production input does.

`GrowthCampaignProgress` retains the parent destination, world/story persistence and party isolation. A finished, quiet, genuine ordinary-party victory with validated, explicitly deferred pending items carries them to the next battle by itself (`deferred_rewards_ready`; there is no result page or button). Open pickup, unfinished presentation and separate-party pending items still block: `hold_for_loot` reopens the get-item window before the battle-end fade, and for a separate party, whose pool cannot travel with it, the notice line says so (`SEPARATE_LOOT_PROMPT`); taking or 放棄 empties the pool and the battle end proceeds. A fresh battle instance resets its box ledger, whereas F9 preserves it; original global never-reopen policy is not asserted. See [source scope](../evidence_packets/static_reverse/original_treasure.md) and [real controls / separate-process recovery](../evidence_packets/runtime_observations/treasure/README.md).

`JobStatsRules`支持公式表里的全部 20 个职业（80–99，表行由原函数返回钉住；新职业是加 `authored` 行，见 [逐步表 #11](../MODDING_LEVELS.md#32-角色职业与招式)）。基础职业及93／95的不同抗性、96／98的独立整数公式和cap均有原函数返回；[主线角色来源](../evidence_packets/static_reverse/original_campaign_actors.md)补25个未放置模板与技能表归属。源32武器的range3CellCircle仍使008原样初始化明确失败，不能以无装备数值夹具替代正式可玩角色。固有飞行来自每条角色声明，036／034不能仅因翼战士职业取得飞行；006／005／008缺失AI策略不借用他人。未声明初始等级仅为pre-birth输入，正式装载按初始阵容／入场成长处理；源属性／出生／永久取得／当前装备／临时增益维持分层，跨战重建来源而不复制战内临时数值。

普通串的`WeaponEffectRules.MANA`只削减目标MP，使用`_apply_strike`已经夹到剩余HP的本击贡献/3。只有贡献换算EXP为正、且该击是串末击或提前致死时才调用原尾部；主攻／反击串分开，末击落空不补发，使用者MP不变。原先取消／附毒顺序保持，各自数据证明独立。新目标MP立即进入下一次AI准备和费用校验，第二行动／读档不重放旧效果。来源、原返回与有界caller见[职业与末击削魔](../evidence_packets/static_reverse/original_mobile_jobs.md)。

BattleRewardRules 只提案携带／掉落与库存交换；出生携带（0x407c86，随出生调级之前）与击杀掉落（0x44f5d3）照原版抽 loop 的全局流 global_rng（不入存档，读档后重掷），交锋通过 _commit_rewards 一次发共享金币、保存实例化待领物和死亡去重记录。当前可控角色击败敌方才发玩家奖励，含反击；死亡清除异常、气力、呼叫和被抽取的库存。原13段字节与重制资格见 [奖励合同](../evidence_packets/static_reverse/battle_reward_inputs.md)。

claim_reward 校验 sequence/revision/实例ID/接收者/原槽位后原子交换，换出物留在待领池。finish_rewards 只关闭／放弃／延期，不另推进回合；正常玩家耗尽或已完成 AI 的既有交接仍是唯一出口。延期物品跨下一次 sequence 保留，重要物品拒绝放弃；终态领取不会改变结果或重发奖励。

BattleCheckpoint 保存唯一 loop 的状态半边（`CONFIG_SHARED` 之外的键，schema v3）和少量表现游标，限制为静止行动、待领取及结果边界；带版本、配置摘要与 SHA-256，写临时文件后原子更名。读档以运行中战斗的 loop 为配置来源：摘要相符后把保存的状态与其配置块合成完整 loop 再校验（`decode(bytes, current)`／`read(path, current)`）。反序列化不允许对象，校验失败先返回不替换状态。Controller 从静止边界或新开场读回，直接恢复领取及已展示 sequence，不执行初始化／掉落抽样／战斗结算；只支持当前配置的单战手动恢复，不承诺跨关、旧版迁移或任意动画中断。

## AI

Script reinforcement creation uses `ReinforcementGrowthRules.prepare`, not manual player allocation. The immutable `entry_growth_data` joins only reviewed jobs and explicitly declared source parameters; a script pair takes precedence, including `[0,0]`. `EntryGrowthRules` mirrors the complete native inference/average/allocation/adjustment helpers with recorded draw order. A per-instance `entry_growth` receipt owns the birth result; its `source_gains` are applied alongside—but never folded into—source profile, permanent gains, equipment and temporary status during every subsequent refresh. Instance kill EXP/gold feed the existing settlement. Birth draws come from the loop's global stream `global_rng` (`GlobalRandomStream`: the original generator 0x458c10／rand 0x458c80 on the words the original keeps at 0x4795d4／0x4795d8), which AI decisions, random positions and the opening's slot shuffle share; it is separate from the saved damage stream and the reward stream, is not saved in a checkpoint and does not ride the campaign carry (lane RNG-A replaced the independent Park-Miller `initialization_rng`).

PlayLoop materializes a proposed insertion batch only after full-footprint placement succeeds. A later invalid proposal leaves no partial new actors or random-state advancement. Event-triggered actors are committed before the next independent action and clear-victory query; Winfail defers recording an outcome while creation still awaits the sole PlayLoop's transaction. Repeated pressure, saves, second actions, actor death/departure and terminal callbacks do not replay birth. Checkpoint signatures include source data; validation replays receipts without applying them and checks current derived values plus the historical RNG chain. Fresh battle carry preserves learned/permanent records and continues the independent initialization stream. Initial-roster and NPC post-combat callers are separate adapters of shared proven kernels, not repeated birth gains. A separate-party battle receives only the stream; the battle-owned `GrowthCampaignProgress` delegates destination/persistence to its parent and updates only that cursor in outgoing carry, retaining the original party and wallet unchanged. Restart retains the incoming baseline. See [birth boundaries](../evidence_packets/static_reverse/original_auto_growth.md) and [growth lifecycle](../evidence_packets/static_reverse/original_growth_lifecycle.md).

`ScriptWaitRules` compiles immutable opening assignments (insert bindings numbered per header symbol, `<symbol>/insertN`, so a mixed-symbol opening such as STORY006's three Enemy23 then one Enemy24 binds the wait round to the right unit) and prepares batches of event wait requests. PlayLoop alone applies them to `ai_wait_remaining`, commits `script_wait_cursor` and stores `last_script_wait`; the source signature is part of checkpoint compatibility. Source setters replace, never add, countdown values. Newly inserted actors consume their own last ordered assignment once, including explicit code/serial writes interleaved with previous-insert writes; later event setters may target that registered actor. Living-instance queries skip departed/dead records without reviving or reindexing historical state. A repeated rendering callback cannot reapply an already-consumed request.

The existing AI retained-target/priority/navigation pipeline controls whether its wait entry is visited. Once visited, the checked original suffix decrements a nonzero count and wakes on missing HP, any status or a near target. A second independent action reevaluates current state; paralysis skips the decision entry, and final resource/status settlement stays with the existing last-action seam. A setter never triggers that tail or changes combat resources, skills, equipment, growth or movement itself. `actWaitPlayer` is a separate specified-object presentation barrier. Old snapshots without the new source signature are rejected without overwriting their files; new encounters compile their own waiting source rather than importing the old battle's cursor. See [source and boundaries](../evidence_packets/static_reverse/original_script_wait.md).

脚本离场由`BattlePresenceRules`向唯一PlayLoop提交：历史数据保留，`departed`单独撤销在场／占用／队列／目标资格。`WinfailScenarioRules`只记录具体unit ID与触发序号；重复消费无效，当前角色离场不为它补第二行动或状态／资源尾部。AI每个新交锋序号同样交给攻击后事件入口，等待／用药不重放旧攻击。场景的已播游标与规则程序、timeline／绑定摘要一起校验；跨战carry沿旧字段白名单不带本战游标。详见[源边界](../evidence_packets/static_reverse/original_script_departure.md)。

`ai_profiles` derives explicit PLAYERS/TYPE/SHAPEDEF declarations, including missing fields and unmapped identities. Target sorting, preferred professions and search radius are source-driven; action parity and chance use the same 1..99 sample. The prior extra 100-bound mage chance has been removed. `_prepare_ai_turn` verifies current identity, strategy, movement-source metadata and every relevant supported skill target before any RNG.
