# Presentation contracts

本页记录输入与可见表现的合同；[架构入口](../ARCHITECTURE.md) 定义状态所有者，[战斗系统](BATTLE_SYSTEMS.md) 定义实际提交。表现只读已结算收据、管理播放游标和未提交草稿。原帧与重制取舍沿 [知识索引](../KNOWLEDGE_INDEX.md) 查对应证据。

## Shared modules

宿魔刀的MP反馈沿每击快照：影响帧前显示本击`defender_before.mp`，之后才取`defender_after.mp`。非零实际损失追加“魔力 −N”，不足三点HP贡献或目标MP0不伪造扣除数字；攻击者没有回血／回魔动画。004／006的原ANIMAL水平位移、减速与XY／缩放序列已编译进现有特写，共用末帧和影响时点；窗口构图缩放及墙钟为明示重制值。四个新增模板都进入死亡消息资源，即使源遗言为空也必须有明确空记录，避免败北收尾失去角色来源。见[源合同](../evidence_packets/static_reverse/original_mobile_jobs.md)与[实玩图证](../evidence_packets/runtime_observations/mobile_jobs/README.md)。

永久道具沿已有物品反馈播放实际取得值，例如“永久攻擊 +2”，菜单／下一行动／成长在该反馈完成后出现；视觉层不抽样。状态页属性栏底部常驻单行永久收益摘要，长内容截在栏内并用悬停显示完整值，五系抗性的悬停说明分别列出原始／永久和最终80上限；四属性与永久获得分开，读档不会重播取得反馈。源字段与截图见[永久能力](../evidence_packets/static_reverse/original_permanent_items.md)。

BattleVitals的ST条按StaminaRules.CAP=60绘制，20／40／60占一段／两段／全满；是否拥有绝技和是否足以付款由PlayLoop的源技能与费用规则给出。装备详情显示凝氣之環的加倍或鬼面的停止效果，确认预览在四项属性之后显示气力积累变化。界面只读当前／提案装备，不保存修饰缓存、不改气力或行动队列。来源和可见验收见 [original_stamina](../evidence_packets/static_reverse/original_stamina.md)。

普通和反击特写从每击attacker_before／defender_before构造显示副本，用本击stamina_gain.before／after在impact切换；无增长的中间一击保留自身快照，不能借下一击或反击的before显示未来ST。无快照的历史合成clip才沿旧counter-before合同。HP／EXP和属性也只修改显示副本，不会提前显示下一击、反击或升级结果。

## Opening and dialogue

`hsl_chapter_dialogue.py --pak <original hsl.pak> --chapter|--level N` extracts cp950 `DATA\RESOURCE.TXT` and resolves chapter messages from its `[name]` table. The live runtime consumes `message_text_evidence.json.messages` and speaker names. The checker compares every imported message to source bytes; historical message-ID-only VM probes are not live text lookup. Product opening advances preparation tokens automatically and waits for confirmation only at dialogue. It reuses the existing presentation timer and timeline cursor.

Opening and battle dialogue share `BattleDialogue`: native BOARD02 and portrait resources and the original handler's text window ([对白框包](../evidence_packets/static_reverse/original_dialogue_board.md)): four 28 px rows at the board's (17,17), the speaker's name as row 0 and the body below it (narration: four body rows). `BattleUISkin.message_rows` breaks the body every 38 source bytes (the row breaker `0x413960`: 19 full-width or 38 half-width characters, `\n` a hard break), except that a break which would cut a proper name from `content/generated/hsl/text/protected_words.json` moves before the name (a remake deviation kept after playtest feedback; the original cuts names). A confirm (`advance_page`) moves the logical page `top_row` at once by the rows left below the window, at most four, and the rows scroll up 3 px a tick (10 ticks a row); a shorter last scroll keeps earlier rows in view. The board fades in and out over 16 ticks and the window's clip wipes in from 17 px by 3 px a tick. Fades, wipe and scroll are visual only: a confirm during them acts at once (the original ignores it — a registered deviation). Repeated refresh preserves the current page. The caller advances its timeline/message only after the last page, and clears the view between messages. The glyphs are the system font at `UISkin.FONT_BODY`, not the original bitmap font. Board placement follows the original handler `0x414280` ([对白框包](../evidence_packets/static_reverse/original_dialogue_board.md)): every line sits at (144,320) whatever the speaker's position; only a script-faced line (`show_face_message` — `actShapeMessage`, the flag `0x4000` that `0x414220` sets) takes the top slot at y 20; speakerless narration (`show_narration`) centres the board at x 75, and a host's remake line that names a speaker without a face passes `centred = false` to keep 144. `show_*` sets the whole position, so a host only overrides it deliberately (the town's top board for `teShapeMessage`).

Battle dialogue is read-only presentation in `BattlePresentation`: `_queue_story_dialogue` pages whatever `BattleScenarioRuleAdapter.story_dialogue_messages(loop)` reports — the fired events' lines and the outcome's win lines or the fallen fail token's dead message, all reported by the `WinfailScenarioRules` interpreter (level 51: WINFAIL051 event 2 396／397, event 3 368／369／370, win 371, dead message 304; levels 52/53: event0 392/393, victory 378, defeat 394; 704 / 694) — deduplicated by `key:message_id`; its message queue and seen-event cursor contain no combat state. Runtime suspends AI stepping and consumes confirm input while messages remain. Result/restart appears after the closing line. Each scenario line's portrait row is resolved when queued from its speaking token (`_story_speaker_actor`: the unit `winfail_runtime.actor_bindings` binds → its current row via `ActorSpriteKey.row_key` against the level portraits, else the `SID_ENEMYnnn` row, else the name-id table `SPEAKER_PORTRAIT_ACTORS` 0/1/2/305/376/377/382/307) — the same rule the level assembler enforces at build time (`hsltools.levels.battle.missing_portraits`). `BattleDialogue.show_message` reports a row missing from the level manifest (`push_error`) and still shows the line without a portrait, so a data gap never leaves an invisible panel waiting for input. Lines a script cutscene already paged are pre-marked (`mark_story_message_shown`), so in the product flow the first battle's event and result lines play through the coordinator cutscene (below) and the story queue only pages what no cutscene consumed. The hand-written first-battle messenger stage (`FirstBattleStoryStage`) is gone: the round-6 messenger is the interpreter's inserted object 10000 walking in, speaking and leaving through the same cutscene machinery as every other level; one living 026 and one living 021 leave with it (`actWalkAndDeleteWait`). The objective line is the winfail board: armed win rows and labelled event rows as 目標 (level 51's hold phase reads 目標：等待援軍到來 from event 3's `message = -1,361`), fail rows as 敗北; the gold escape cell appears only once an arrival win status is armed (`WinfailScenarioRules._refresh_objective`).

Script cutscenes (winfail result chains) reuse the opening machinery. `hsltools.levels.scenario.status_timelines` (called by every scenario assembler) compiles every winfail status' result chain into `scenario_rules.status_timelines[<kind>_<code>]` (the same event shape as the opening timeline; tokens the interpreter applies to the loop are flagged `cutscene_skip`, messages and departures stay playable). When `WinfailScenarioRules` fires a status — round hook, strike or the outcome the PlayLoop commits in `_resolve_outcome` — the entry lands in `winfail_runtime.fired`; `BattleSceneRuntime.maybe_start_script_cutscene` consumes fired entries by index at the next idle frame (no actor motion, combat, item feedback, dialogue or loot pending) and hands the timeline to `BattleOpeningCoordinator.start_cutscene`, which pages messages through the script message box (camera on the speaker), waits `actDelay`, walks / walks-and-deletes bound actors, scrolls the camera and plays sounds with the opening handlers and remake pacing; the runtime's `_process` early-returns while it is active, so AI playback, menus and the battle end wait. On finish an undecided battle resumes `resume_turn_presentation`; a decided one sets `battle_finished` and fades out. The only exception is the event-only hand-off: when the finished cutscene belongs to the status recorded in `play_loop.next_level_event_status` (the fired status whose chain wrote `actSetNextPlayLevelEvent` — WINFAIL073 event_2, WINFAIL078 event_3, WINFAIL900 event_0), the coordinator ends the scene through `_finish_story` with that token; the win-section default token never does, so a dialogue-only event such as WINFAIL010 event_3 at round 5 resumes the battle (a token-bearing status with no playable events hands off at consumption instead). Messages the cutscene paged are pre-marked in `BattlePresentation.mark_story_message_shown` (`<status key or outcome>:<message id>`) so the story queue never repeats them; departed units (`winfail_runtime.departed_unit_ids`) stay hidden through the apply_loop mirror step (`_sync_from_play_loop`) while their roster record remains with the PlayLoop (consumption in the turn queue is a pending request). The developer switch `HSL_CUTIN_PLAYBACK_SPEED` (e.g. `0.4`) slows the whole cut-in for frame review; `CombatPresentationTiming._read_playback_speed` is its only read site, and every scaled-clock lead (`CAST_LEAD_IN` 1.1 s — the magic presenter's stand-in for the m_action lead of a caster whose m_shape strip is not imported; the moon-dance `intro` 1.5 s, the poison-arrow tick) goes through `Timing.scaled` so its visible length does not change with the switch; the 絶技 cast lead and the imported m_action leads are tick-driven (`AnimalCastLead`) and need no stand-in. `PYTHONPATH=tools python3 -m hsltools.assets.combat_animation --bind-programs` binds the current six actor types without reimporting SHP pixels. Delay setup/wait/exit, SetShape yielding and Flash continuing in the same call are distinct; unknown ordinary opcodes are rejected, not skipped. It owns no combat state. `released` triggers the swing sound; `impact` triggers weapon-category hit audio and the existing settled receipt feedback. At 30/60 display fps the shared contract tests verify independent visible receiver intervals, event order and no state mutation. Source-loader termination, the native shared tail and receiver dispatch remain outside this binding.

## Results

战斗中脚本由`BattleScriptPresentation`保留尚待离场的图像、预留对白并阻止输入；`BattleDepartureView`只对PlayLoop已有离场收据的角色执行 16 tick（0.256 s）淡出。Coordinator按P-031在行走删除、直接删除与tick完成条件三处使用可空委托，story-only／世界／城镇不变。离场 16 逻辑 tick 经 `OriginalTick`（16 ms）换算，淡出形式是重制渲染。当前交锋／领取／成长先结束，脚本再播放，下一角色／第二行动／结果最后出现；读档清理旧演出并恢复已播游标，不复建离场角色。没有开场的开发场景首次触发事件时创建同一Coordinator。见[实玩图证](../evidence_packets/runtime_observations/script_departure/README.md)。

战内道具提示由`BattleItemText`读取预检或已提交收据；首次随机强化的预览保留区间，提交后只显示真实数值／延长时间，不用HP变化推测成功。破魔和气力反馈不会伪造+0HP，既有物品声和阻塞段完成后才显示下一行动。装备页名称按实际编号从统一目录读取，合法最小槽记录不再导致缺name错误。实际恢复／终态与[17条道具流程](../evidence_packets/runtime_observations/tactical_items/README.md)分别标注。

攻防／退魔使用`StatMagicPresentation`的37源图帧和9源声音，粒子布局与时钟仍是重制值。新三法术的状态数字仅由impact不可变收据触发；后继菜单／成长／结果等待最后可见帧完成。Vitals最多五状态分两行，状态页保留总值并标示固定加值，到期以TurnEndCue独立显示减少值。[实际图证与过程边界](../evidence_packets/runtime_observations/stat_magic/README.md)。

麻痺入场通过既有NavigationCue显示“麻痺 · 無法行動”，先于相同槽的毒伤／资源／到期反馈；有限播放结束后才开放后继。地靈縛使用独立ParalysisMagicPresentation消费源8帧／2声音和真实接收者位置；分布、混合与时钟为重制编排，释放／impact各一次，末帧完全淡出。到期或精靈石只显示“麻痺解除”，不显示0HP回复；状态栏显示当前剩余次数。共用busy现在也包含物品反馈，修复“无资源尾部时用药文字尚未结束便开放下一菜单”的实玩回归；剧情／结果也等同一门禁。见[实玩与图证](../evidence_packets/runtime_observations/paralysis/README.md)。

移动后施法资格来自PlayLoop当前阶段及装备。无权限的拥有法术者在合法移动格预览看到“移動後不能施法；取消可返回原位”，移动后的菜单移除魔法项；装备预览分别说明施法资格与普通／反击范围提升，法术范围不扩大。文字和范围均只读，不能为了重建菜单清除移动标记。禁魔／不足MP的既有禁用列表仍为可读性选择；[位置能力实际输入](../evidence_packets/runtime_observations/position_equipment/README.md)记录取消、装卸、第二行动和终态图证。

施法装备的尾部数字由`BattleTurnEndCue`读取不可变事件：毒伤及两类自动回复完成后，血衣依次红色失血数字、蓝色回魔数字（只有数字，无“轉化／中毒”说明与 HP／MP 后缀——UI6 照原版；无符号字形，颜色分损益，`ShowNumberStyle`）。满MP不伪造正向数字，1HP无损时只正常交接。装备预览／状态说明写明满魔仍耗生命、防护不清已有状态，沿既有滚动区域显示；不让视图重算效果或提前显示后续资源。源函数／样例与[实玩图证](../evidence_packets/runtime_observations/casting_equipment/README.md)分别记录。

`BattleAftermath` 在 EXP 后显示已提交金币；金币／掉落不在展示层抽样。收尾结束后，`BattleSettlementController` 读取 PlayLoop 的未关闭 settlement 打开 `BattleLootPanel`，暂时阻塞成长、AI、结局对白与后继菜单。空掉落跳过面板；有掉落时完成或延期后继续既有交接，末敌胜利也先处理领取。

`BattleLootPanel` 按原作 status mode 0xb 的 獲得物品 窗排版（[static 证据](../evidence_packets/static_reverse/original_getitem_window.md)）：顶部 `BattleVitals` 生命条＋姓名窗；左 WINDOW20 (12,168) 为领取者背包八格（图标锚 (44,184+32i)、名字 x=68）；右 WINDOW90 (252,168) 标题“獲得物品”居中、五行 (code, 数量) 列表——图标 (284,225+32i)、名字 x=308、数量右对齐到 x=584、名称颜色按原作 重要@6／本职可用@1／否则@2；下方 WINDOW50 (252,390) 为悬停说明框，WINDOW40 (20,442) `$:` 钱窗；BCMD08／15／14 三个 42 px 图标按钮居中 285／346／468、y 429，15 px 说明字在图标下 13 px，悬停变黄。交互沿原作“拿起—放下”：点列表行拿起一件（图标随光标、TAKEUP01），点背包格放下（PUT00003；占用格即交换，被换出物回到列表）；右键／Esc 在持物时放进第一个空格（原 root 窗 case 1），空手时不关窗；持物时点列表或 倉庫 把物品放回池。领取者固定为原作语义的杀敌者／开箱者，Status→獲得物品 重开时切换为当前查看成员。刻意差异：原作 倉庫 送入仓库、丟棄 丢弃当前持物；重制没有仓库，倉庫 = 放回，丟棄 = 二次确认后放弃全部剩余（重要物品在池时禁用，且光标离开图标即取消确认）；离开 按钮只在空手时可按，剩余物品延期到下次 Status。数量列合并同 code 条目为一行，PlayLoop 仍逐件 claim。

There is no result page or next-battle button (the original leaves a won battle through 0x42cc10 straight into the screen transition). Once the victory has finished and faded, `BattleSceneRuntime.leave_finished_battle` calls `CampaignProgress.start_next_battle`, which resolves `next_level_event` through `campaign.json`, captures the controlled party, stores the one-shot `pending` hand-off, persists the same record to `user://campaign_progress.json` and reloads the scene into the next scenario. A fresh launch of the campaign's first battle (`product_opening`) with a persisted position further along pauses the tree under a resume prompt on an always-processing layer — 「繼續 · <title>」turns the saved record into `pending` and reloads, 「從第一戰重新開始」deletes it; see [campaign hand-off](../evidence_packets/runtime_observations/campaign_handoff/README.md).

领取面板只有接收者、选择和确认草稿，默认接收者优先获奖角色。真实 sequence/revision/槽位仍由 PlayLoop 校验；每次重建／关闭／读档都会使旧控件失效。满包交换的换出物留在待领池；放弃普通剩余物需要第二次确认，重要物品不可放弃，延期后可在状态页重新打开；胜利结束时池里仍有带不走的物品，领取窗会先重新打开。

状态和领取页有 F5 保存／F9 读取，启动开场有存档时显示“繼續存檔”。保存只允许安静边界；读回会恢复单一 loop、镜头与故事／成长游标，并把旧战斗／奖励标为已展示。新进程加载和终态恢复不重放金币／经验，结果音乐的旧渐隐会先取消。存档不覆盖原作文件，不提供任意动画中途恢复或跨关兼容。

`BattlePresentation` derives the dimmed result panel and retry button from the final visible result after cut-in and original closing dialogue. Runtime suspends map/menu input at that boundary and shares `_restart_battle` between Enter and the real button. Failure's first visible transition plays the imported `sfxGameOver` through the existing interface sound player; no new outcome state, transition flag or audio scheduler is introduced. The result layout and cue timing are remake choices.

Runtime checks cover deferred result/audio, non-repetition, stale-menu suppression and fresh state after restart. Rendered fixtures verify readable victory/failure layouts and mouse restart. Test-only mixer cleanup is not a production lifecycle or a game timing contract.
