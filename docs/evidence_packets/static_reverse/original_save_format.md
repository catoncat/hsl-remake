Evidence tier: `static-derived` from a bounded read of the save writer `0x42e070`, the reader `0x42e640` (peek/load wrapper `0x42ec10`), the block compressor `0x45b016` with its decompressor `0x45b089`, and the checksum `0x42e040` in `hsl01.exe` (sha256 `f0b5f835…`). The layout is anchored by one real file the original wrote under Wine (`runtime-measured`): [`original_save_format/HSLBAT_first_control.SAV`](original_save_format/HSLBAT_first_control.SAV) with its parsed summary [`HSLBAT_first_control.json`](original_save_format/HSLBAT_first_control.json). `python3 tools/hsl.py check original_save:sample` re-parses and re-serialises that file and fails unless the bytes are identical (`ORIGINAL_SAVE_CHECK_PASS`). ## File layout

Every compressed block is `u32 length` followed by `length` bytes of the block codec below; the reader passes a fixed expected size (`0x42e640`), so block sizes are part of the format.

| # | Section | Size (decoded) | Original owner | Notes |
| --- | --- | --- | --- | --- |
| 1 | header | `0x68` | the `0x42e070` field list (table below) | version word 100 |
| 2 | registered slot codes | raw `0x54` | `0x4c4360[21]` (i32) | 0 empty; `800 + slot` after `0x450710` registers a pmPlayer object; `0x4348f0` → `0x42c700(slot, up code)` replaces it by the consumed `obj_Player<N>Up<tier>` code (`818` / `819` after the second titles, native); bit 31 set = registered but disabled |
| 3 | player-mode bytes | raw 200 | `0x4c6d80[200]` | one byte per live actor index; the sample sets index 0 (雷歐納德) and 23/24 (two level-51 actors) |
| 4 | live actor records | `0x18edc` = 201 × `0x1fc` | `*0x4c1bc8` | registered slot `n` lives at index `n + 1`; `0x44cb10` installs battle actors from index 21 upward |
| 5, 6 | two item lists | `u32 capacity`, `u32 count`, then LZW(`capacity × 8`) | `*0x4c1d10`, `*0x4c1d1c` (`0x44f720` lists) | new game: capacity 5, count 0 |
| 7 | encounter ratios | 200 = u16[100] | `0x4c27e0` | per big-map point (`0x4545c0`, `BMSetPointEncounterRatio`); new game 10 |
| 8 | town menu trees | `0x6720` = 100 × `0x108` | `*0x4c1d74` | per town: the menu tree (`teAddTE`/`teDeleteTE`), u16 `+0x100` exec event (`0x454740`), u16 `+0x102` exit exec event (`0x454780`); see [original_world_town.md](original_world_town.md) |
| 9 | big-map points | 4000 = 100 × 40 | `0x4c4a20` | the `bigmap.dat` point table with live mode / flags / event words (`+0`, `+4`, `+8`) |
| 10 | big-map tracks | `0x640` = 100 × 16 | `0x4c43c0` | the `bigmap.dat` line table with live mode / flags |
| 11 | battle tail | variable | `0x4079f0` queue, `0x44e970` flag tables, per-object records | 戰場記錄 only; the codec keeps it verbatim (`battle_tail`) |
| 12 | checksum | `u32` | `0x42e040` | over every byte before it |

The 讀取回憶錄 / 儲存回憶錄 list row is rendered from the header alone (`0x42ec10(slot, 0)` peeks the header and restores the globals): point name from `0x4c1ba4`, `等級` from `0x30`, the clock from `0x34`.

## Block codec (`0x45b016` / `0x45b089`)

`tools/hsltools/data/_original_save_codec.py` reproduces the compressor instruction for instruction: an LZW variant with 9..13-bit codes emitted LSB-first (`0x45a8bc`), escape code `0x100` followed by 1 (width grows) or 2 (dictionary prune), dictionary codes `0x101..0x1fff` kept as a first-child / next-sibling tree with a free list (`0x45a7b0` init, `0x45abd5` step, `0x45aad7` add, `0x45ab7e` lookup, `0x45aa43` / `0x45a925` prune), blocks shorter than 10 bytes stored verbatim, and the sliding-dword XOR checksum `0x42e040`. It is not a generic LZW; the sample round trip is byte-identical only because the tree order, free-list order, width growth and prune order match.

Native cross-check (`runtime-measured`, unicorn on the mapped EXE, 2026-09-21, `ignored/r9-save/native_lzw_check.py`, not tracked): on 12 inputs — zeros, random bytes, a 26 400-byte periodic block, a 30 000-byte random block, a 102 108-byte skewed block, and the six blocks of the generated 回憶錄 — the original `0x45b016` produced exactly the Python encoder's bytes, and the original `0x45b089` decoded every Python-encoded block back to its input.

`HSLBAT_first_control.SAV` (6178 bytes, sha256 `97546502…`) was written by the original (v1.06, Wine) from the battle scroll 儲存戰場記錄 at 雷歐納德's first action menu of level 51 (first control), i.e. the fresh new-game tables after the new-game reset (`bigmap.dat` copied into the point / track tables, gold 1000, slot 0 = 800, encounter ratios 10) plus the level-51 placement. Levels, attributes and inventories are fixtures (`provisional`), chosen so the `0x434770` test holds exactly where the preset claims it; the replayed flow covers only tokens that write saved tables (`actSetNextPlayLevelEvent` and presentation tokens are listed as skipped).

**Level-entry header (`static-derived`, `entry_level` presets).** A level that is not a big-map point (the 51 → 52 → 58 → 60 → 53 prologue chain) is reached only through `actSetNextPlayLevelEvent level,event` → `0x42cc10(level, event)`: `0x4c1ba8` (next level) = `level`, `0x4c1bac` (level files) = `event`, then the level-switch request. The main loop `0x42f7a4` sets `0x4c1ba4` (current point) to `walk_from_point`, or to `0x4c1bb8` (current level) when that is −1 (and to 1 when the result is 0), and calls the level runner `0x42da60(next_level)`, which stores `current_level = next_level` and loads WINFAIL / OBJ / ICO / WRD / BIN / STORY of `level_files` (`0x42ce10`). 讀取回憶錄 goes through the same runner: `0x42ccc0(slot)` records the pending slot in `0x4c1ae4` and requests the switch; `0x42da60` performs the load (`0x42ec10(slot, 1)`, which restores `0x4c1ba4` / `0x4c1ba8` / `0x4c1bac` / `0x4c1bb8` from the header), and the loop's next `0x42da60(next_level)` runs the saved level with the saved files — which is how the big-map presets (`level_files` 49) reach the map from inside the level-51 battle (`runtime-measured`, R9 / R11 / R14). `level_entry_header` therefore writes `next_level = level_files = current_level = entry_level`, `walk_from_point −1`, `walk_to_point 0`, `show_track_point 0`, camera 0 / 0 and `current_point 1` (the list row's point name; the tracked HSLBAT sample carries `current_point 1 / current_level 51` the same way). Wine load of `level53_pre_battle` (`runtime-measured`, 2026-09-22, lane R33, route in [battle_053](../runtime_observations/battle_053/README.md)): the 讀取回憶錄 row read 歐姆村 等級01 0:15; one click entered STORY058 directly with `0x4c1bb8 / 0x4c1ba8 / 0x4c1bac` = 58 / 58 / 58 and `0x4c1ba4` = 1 (the header word stayed; the loop did not rewrite it before the level ran), STORY058 → STORY060 → level 53 chained natively, and level 53 installed 緹娜 from the PLAYERS 002 row (L2 36/36 by the install-time level inference). Not derived: whether the original ever writes such a header itself (a 回憶錄 can only be saved on the big map or in a town).

**A battle level cannot be entered this way (`negative-evidence`, `runtime-measured`, 2026-09-23, lane M1).** A header with `next_level = level_files = current_level = 5` (呼嘯平原, a battle level, not a story-only one like 58) loads STORY005 with the four registered party records exactly as written (001 L7 39/39 attack 82 defense 54 speed 19, 002 L4 38/38, 003 L6 42/42, 004 L7 50/50), but the nine EVEF enemies sit in live slots 21–29 with **uninstalled records** (code 0, L1, HP 1/1), and the first player 待機 fires WINFAIL005's `actCheckEnemyTotalNumber,0` win section (903 / 904) and returns to the big map. The same enemies are installed normally when level 5 is reached from the big map (point preset above: codes 36 / 38, L4–L8, 52–94 HP). So `entry_level` only works when the entered level is story-only and the battle is reached by the native `actSetNextPlayLevelEvent` chain (58 → 60 → 53); to start a battle that is a big-map point, stand on the neighbouring point with the battle point unvisited. Why the post-load level run skips enemy installation is not traced (`0x42ec10(slot, 1)` → `0x42da60` path).

The item flag word uses the bits `equipment.py` already names plus the three the 66 templates pin (`action_twice 0x8`, `double_attack 0x8000`, `mp_auto_restore 0x200`); an item declaring any other boolean without an evidenced bit makes synthesis fail loudly rather than guess.

## Live actor records: the PLAYERS template dump and member synthesis

The original never builds a live record from PLAYERS.TXT at install time: the parser fills a **template table** `*0x4c1afc` (201 × `0x1fc`, index = PLAYERS code) once at start-up, `0x44cb10(index, 1)` copies template → live for the same index ([original_priest.md](original_priest.md), [original_campaign_actors.md](original_campaign_actors.md)), and the constructor `0x407ec0` then writes its install-time words and calls the refresh `0x448840`. A registered party slot `n` is live index `n + 1`, i.e. PLAYERS row `n + 1` (`0x407eff`).

**Dump** (`runtime-measured`, 2026-09-21): `ignored/bin/hsl_win32_memread.exe --read-bytes templates=<*0x4c1afc>:0x18edc` (the helper's new bounded byte-range read, `ReadProcessMemory` on the running Wine original standing on the big map; raw JSON in `ignored/r11-save/dump_bigmap_point33.json`, not tracked). 66 of the 201 slots were non-zero — exactly the 66 PLAYERS.TXT rows, each at index = its code. They are tracked as [`original_save_format/PLAYERS_templates_runtime.bin`](original_save_format/PLAYERS_templates_runtime.bin) (66 × 508 bytes in code order) with [`PLAYERS_templates_runtime.json`](original_save_format/PLAYERS_templates_runtime.json) (sha256, codes, the handle rule and the name → handle map). The live table `*0x4c1bc8` dumped alongside had only index 1 (雷歐納德) filled although slots 0–4 were registered: registration (`0x42cb30`) writes the slot code only, the record is filled at the next battle install — which is why an all-zero record of a registered slot showed as an empty `等級0` member in R9's Wine run.

`python3 tools/hsl.py check original_save:members` (`ORIGINAL_SAVE_MEMBERS_PASS templates=66 fields=3432 handles=87 synthesized_001=sample`) proves, from tracked data only:

- template `001` differs from the live record the original wrote into the tracked HSLBAT sample by **one dword**: `+0x14` = `304 << 16` (the install-time dead-message word `0x407ec0` writes for a player; RESOURCE 304 is the generic dying line). Level actors additionally carry `+0x84` = their code (install-time) and the level's own item / mode writes; the templates have `+0x84` = 0 and `+0x134` = 0.
- every template field the generator relies on equals its PLAYERS.TXT column (code, name id, job, job_show_name, class, mode, size_type / carry_item, job_up_code object, the four attributes twice, level, exp, kill_exp, gold, stamina, six equipment words, five base resists, move, eight items) — 52 fields × 66 rows;
- the derived layer of every template (caps `+0x74..`, max HP / MP, attack, defense, speed, hit ratio, magic attack, move work, five working resists, exp threshold and the three `+0x19a/+0x19e/+0x1a2` work halves) is re-derived **byte for byte** by `hsltools.model.jobs.calculate` — the independent `0x448840` model the native probes already cross-check — from the record's own job, mode, base attributes, equipment, base resists and additive layer (`record_profile` reads them from the record: `+0x1a4..+0x1b0` dwords, the signed `+0x1b4`/`+0x1b6` MP / HP pair — PLAYERS 066 declares `hit_point -10000` — and `has_magic` = any of the six magic words `+0x174..+0x188`);
- the eight resource-handle words match the rule below for all 66 rows;
- `synthesize('001')` (template copy + `+0x14`) equals 雷歐納德's live record in the HSLBAT sample byte for byte.

### The resource-handle words (`static-derived` rule, verified on the dump)

The words R9 could not derive are PAK directory positions, assigned by the resource loader from the sorted archive directory — not RESOURCE.TXT ids and not raw PAK record indexes:

| record word | half | PLAYERS.TXT column | value |
| --- | --- | --- | --- |
| `+0x08` | lo / hi | `sound_walk` / `sound_dead` | WAV handle |
| `+0x0c` | lo / hi | `sound_miss` / `sound_attack` | WAV handle |
| `+0x10` | lo / hi | `sound_hit` / `sound_walkwater` | WAV handle |
| `+0x20` | lo / **hi** | class (`+0x20`, TYPE.H `classHuman` 101 …) / `sound_shoothit` (`+0x22`) | class word / WAV handle |
| `+0x5c` | u32 | `picture` | shape handle |

WAV handle = `1 + index` of the name in the case-insensitive sort of the 220 `@:\wav\` PAK names (0 = column absent): `Attack01.WAV` → 5, `Attack05.wav` → 7, `Dead0003.wav` → 54, `Miss0001.wav` → 136, `Walk0011.wav` → 187, `Walk0012.wav` → 188, `FLY003.WAV` → 89, `BOMB0028.WAV` → 44. Shape handle = index of the name in the case-insensitive sort of all 4519 `*.shp` PAK names: `face0000.shp` → `0x1075`, `face0001.shp` → `0x1076`, `FACE0020.shp` → `0x1089`, `face0021.shp` → `0x108a`. The rule fixes R9's provisional readings of `+0x20/+0x22` ("two word fields following the title") and `+0x10`; `+0x14` is the `dead_message` pair (`hi` = first id, `lo` = second) for rows that declare it, else 0 in the template and the install word for players.

The generator does **not** need the rule: it copies the handle words from the dumped template of the member (and of the job-up target, as `0x4348f0` does). The rule is recorded so the words are no longer opaque; `resource_handles` in the summary JSON is the name → handle map the check uses (the PAK itself is only read when the dump is rebuilt with `HSL_ORIGINAL_MEMORY_DUMP=<json> hsl generate original_save:members`).

### Member synthesis (`hsltools/data/original_save_members.py`)

`synthesize(templates, member)` mirrors the original order: template copy → `+0x14` player word → spec `level` / `exp` / `attributes` (written to both the working `+0x4c..` and base `+0x64..` rows) / `inventory` (eight slots) / `equipment` → `0x448840` refresh with HP / MP set to the maximum (including the `+0x18c` effect-flag rebuild) → one `0x4348f0` exchange per `job_up_history` entry (first tier `0x80000000`, second `0x40000000`; each tier is admitted only while `record+0x60` names the matching `obj_Player<N>Up<tier>` object of OBJ-ALL.H; the exchange also reports the consumed up code, which `apply_spec` writes into the slot code as `0x42c700` does) followed by the refresh again. The exchange follows the field table of [original_town_job_up.md](original_town_job_up.md) with the **target template** as source, so 緹娜's second title carries `FACE0020`'s handle `0x1089` and 017's own sounds. Party entries use the remake's carry vocabulary (`actor_id`, `level`, `exp`, `attributes`, `inventory`, `equipment`, `job_up_history`); the registered slot is `code − 1`.

Not derived from evidence (`provisional`): the `+0x14` word of members other than 雷歐納德 (set to his observed value; `0x407ec0` rewrites it at the next install), member levels / attributes / inventories of the presets (fixtures at the `0x434770` margin, not a recorded playthrough), and the two shared item lists (kept at the new-game capacity 5 / count 0 — the story items are placed in a member's eight slots, which `teCheckItemExecEvent` `0x454cd0` also searches).
